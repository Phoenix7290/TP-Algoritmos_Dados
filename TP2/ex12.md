# Exercício 12 — Decisões de Projeto e Complexidade

---

## 1. Operações da Trie — Complexidade em Big O

| Operação | Custo | Variáveis | Observação |
|---|---|---|---|
| `insert(word)` | O(m) | m = \|word\| | Desce/cria m nós; sem backtrack |
| `search(word)` | O(m) | m = \|word\| | Desce m níveis e verifica `is_end` |
| `starts_with(prefix)` | O(p) | p = \|prefix\| | Equivale a `_find_node`; não coleta palavras |
| `_collect_words(node, prefix)` | O(N) | N = nós na subárvore | DFS completa; proporcional ao tamanho da subárvore |
| `autocomplete(prefix, k)` | O(p + N + W·log W) | W = palavras na subárvore | `_find_node` + `_collect` + `sorted` + `[:k]` |
| `autocorrect(word)` | O(m + N + W·log W) | m = caracteres descidos | Desce até divergência, depois coleta e ordena candidatos |

---

## 2. Lista vs Matriz de Adjacência — Comparação

| Operação | Lista de adjacência | Matriz de adjacência |
|---|---|---|
| Inserção de aresta | **O(1)** amortizado — `adj[u].add(v)` | O(1) se V fixo; `add_vertex` custa O(V) |
| `has_edge(u, v)` | O(grau(u)) — busca no conjunto de vizinhos | **O(1)** — acesso direto `mat[i][j]` |
| Iterar vizinhos de u | **O(grau(u))** — percorre apenas vizinhos reais | O(V) — varre a linha inteira mesmo com zeros |
| Memória | **O(V + E)** — eficiente para grafos esparsos | O(V²) — desperdiça zeros quando E ≪ V² |
| `add_vertex` dinâmico | **O(1)** | O(V) — expande cada linha da matriz |

---

## 3. Qual Representação Escolher?

### Grafo esparso com milhões de vértices → **Lista de adjacência**

Quando E ≪ V², a matriz desperdiçaria O(V²) células.
Para V = 10⁶, isso equivale a 10¹² entradas — aproximadamente 8 TB apenas para armazenar inteiros de 8 bytes.
A lista de adjacência usa O(V + E): com E = 5·10⁶ arestas, a estrutura inteira cabe confortavelmente em RAM.

**Exemplo concreto:** grafos de redes sociais, grafos de dependências de pacotes, grafos de páginas web (PageRank).

### Grafo denso com poucos vértices → **Matriz de adjacência**

Quando E ≈ V² e V é pequeno, a diferença de memória é desprezível.
O acesso `has_edge` em O(1) é valioso quando há muitas consultas ponto-a-ponto sobre um conjunto fixo de vértices.

**Exemplo concreto:** grafo de dependências entre 50 módulos de um sistema, tabela de distâncias entre cidades num problema de roteamento.

## 4. Decisões Técnicas Justificadas

### Decisão 1 — Trie: `children` como `dict`, não array de 26 posições

A implementação clássica de Trie usa um array fixo de 26 slots (um por letra do alfabeto latino). A escolha de `dict` foi deliberada por dois motivos:

- **Memória:** um array de 26 ponteiros aloca 26 entradas por nó independentemente de quantos filhos existam. Para vocabulários com caracteres não-ASCII (como hifens em `"auth-service"` no Ex. 11), seria necessário ampliar para 128 ou mais slots.
- **Generalidade:** o `dict` suporta qualquer caractere sem nenhuma mudança no código. O custo de acesso permanece O(1) amortizado via hash.

O único custo é o overhead por entrada do dicionário (~50 bytes por entrada vs ~8 bytes num array de ponteiros), aceitável para vocabulários de tamanho razoável.

```python
# Escolha adotada
self.children: dict[str, TrieNode] = {}

# Alternativa rejeitada
# self.children: list[TrieNode | None] = [None] * 26
```

### Decisão 2 — Trie: desempate do `autocorrect` pelo menor lexicograficamente

Quando dois ou mais candidatos compartilham o mesmo prefixo máximo com a palavra incorreta, a função retorna `sorted(candidates)[0]` — o menor lexicograficamente.

Alternativas consideradas e rejeitadas:

- **Retornar a palavra mais curta:** menos previsível para o usuário; duas palavras de mesmo comprimento geram novo empate.
- **Retornar a primeira inserida:** não determinístico — depende da ordem de inserção, que é um detalhe de implementação invisível ao chamador.

A escolha lexicográfica é **totalmente determinística**: mesma entrada sempre produz mesma saída, independente da ordem de inserção ou do percurso da DFS. Isso torna a função pura e auditável.

```python
candidates = self._collect_words(node, prefix)
return sorted(candidates)[0]  # desempate: menor lexicograficamente

# Garante: autocorrect(word) é função pura — sem dependência de estado oculto
```

### Decisão 3 — Grafo: vizinhos armazenados como `set`, não `list`

A escolha de `set` em vez de `list` para armazenar os vizinhos de cada vértice torna `has_edge` O(1) amortizado na lista de adjacência (contra O(grau(u)) com `list`).

Custos aceitos da escolha:

- **Perda de ordenação natural:** compensada pela ordenação explícita em `to_mermaid` e nas funções de coleta.
- **Impossibilidade de multigrafos (arestas múltiplas):** fora do escopo deste trabalho.

Para o caso de uso (grafo simples, consultas frequentes de vizinhança), `set` domina `list` em todas as operações relevantes.

```python
self.adj: dict[str, set] = {}

# adj[u].add(v)  → O(1)
# v in adj[u]    → O(1) amortizado
# vs. list:
# adj[u].append(v)  → O(1), mas v in adj[u] → O(grau(u))
```

### Decisão 4 — Mermaid: regra `(min, max)` para deduplicação de arestas

Para grafos não-dirigidos, cada aresta `{u, v}` é armazenada nos dois sentidos na lista de adjacência. Sem controle, `to_mermaid` emitiria cada aresta duas vezes.

A regra adotada — inserir a chave `(min(u,v), max(u,v))` em um conjunto `seen` e emitir a aresta apenas na primeira ocorrência — garante exatamente uma linha por aresta, independente da ordem de iteração.

Alternativa rejeitada: emitir apenas quando `u < v` diretamente na condição. Isso funciona para strings, mas falha para vértices numéricos onde a ordem lexicográfica e a ordem numérica divergem (ex.: `"9" > "10"` lexicograficamente, mas `9 < 10` numericamente). A abordagem com `seen` é **agnóstica ao tipo do vértice**.

```python
def to_mermaid(self, directed=False) -> str:
    arrow = "-->" if directed else "---"
    lines = ["graph TD"]
    seen = set()
    for u in sorted(self.adj):
        for v in sorted(self.adj[u]):
            key = (min(u, v), max(u, v)) if not directed else (u, v)
            if key not in seen:
                seen.add(key)
                lines.append(f"    {u} {arrow} {v}")
    return "\n".join(lines)
```
